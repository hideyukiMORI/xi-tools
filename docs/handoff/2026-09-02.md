## 2. 規約に触る前に知っておくこと

### 🔴 抑制は二段構え。1段目には逃げ道が無い

| 段 | 水準 | 抑制 |
| --- | --- | --- |
| 1段目 | `forbid` | **不可能**。`#[allow]` も `#[expect]` も `E0453` で落ちる |
| 2段目 | `deny` | `#[expect(<lint>, reason = "<規則 ID>: <理由>")]` **のみ** |

⇒ **`forbid` した規則で詰まったら、それは設計の問題である。**抑制する手段が無い。
どうしても要るなら ADR を書いて `deny` に降ろす。**黙って降ろさない。**

### 🔴 `reason` の規則 ID は実在チェックされる

`xtask` の `CNF-006` が `docs/coding-rules.md` に**その規則 ID が実在するか**を見る。
存在しない ID を書くと CI が落ちる（実測済み）。

⇒ **規約から規則を消すと、それを引いていた抑制が落ちる。** 片側だけ動く経路が無い。

### 🔴 `planned` を `active` と書き換えない

規約には現在 **planned が16箇所**ある。これは「まだ機械が見ていない」という意味で、
**その行に触る変更は PR で人が自己レビューする**（`.github/pull_request_template.md` に一覧）。

未実装の強制を実装済みに見せるのは、規約全体の信頼を壊す唯一の行為である。

### 🔴 設定に項目が在ることは、検査が効いていることの証明ではない

実際 `cognitive_complexity` は「`clippy.toml` に閾値だけ設定され、lint 本体は無効」
という死んだ状態だった（`nursery` 群にあり、どの既定群にも入らない）。

⇒ **ゲートを足したら、意図的な違反で発火することを確認**して
[`docs/quality/gate-proofs.md`](../quality/gate-proofs.md) に実出力を残してから active と書く。

### 🔴 `xtask` を触るなら: 検査器は自分自身も検査対象

検出語を `xtask/src/check.rs` にそのまま書くと、**検査器が自分自身を違反として報告する**
（初版で7件出た）。検出語は `concat!` で分割して書く。
ファイル単位の除外で黙らせると、**そのファイルだけ他の CNF も効かなくなる**ので採らない。

また `.rs` は**桁 0 の `#[cfg(test)]` より後を見ない**。テストは意図的な違反を書く場所で、
そこを検査すると検査器のテストが検査器に落とされる。

## 3. 実装を始めるときに待っている摩擦（予告）

規約は**書き味を犠牲にして**一意性を買っている。`scopegrep` はオフセット計算が主な仕事なので、
最初に当たるのはここだと予想している（ADR 0001 の「払うもの」に記載）。

| 規則 | 何が禁止か | 代わりに |
| --- | --- | --- |
| RS-005 | `v[i]` の添字アクセス（forbid） | `v.get(i).ok_or(...)?` |
| RS-007 | `as` による数値変換（forbid） | `u32::try_from(x)?` |
| RS-018 | 型注釈の無い数値リテラル | `1_usize` のように書く |
| RS-016 | `HashMap` / `HashSet` | `BTreeMap` / `BTreeSet` |
| RS-011 | 認知的複雑度 10 / 関数 60行 / ネスト4 / 引数4 | 関数を割る |

⚠️ **通らないから緩める、をやらない。** 通し方が分からなければ聞く（CLAUDE.md 地雷4）。
`xtask` 自身がこの規約下で書かれているので、**書き方の実例として読める**。

## 4. 未決事項（施主の判断待ち）

### ⚠️ ADR の位置づけ（PR #1 で提案中）

CLAUDE.md は「**ADR 形式は取らない**」と書いているが、`docs/adr/` を作った。

**こう解釈した**: あれは「**ツールの設計判断**は `docs/design/<tool>.md` に書く」という規約で、
**ゲートの判断はそれとは別の対象**。QLT-005 が「ゲートを弱める変更は ADR を要する」と
定める以上、置き場が要る。⇒ 設計は `docs/design/`、ゲートは `docs/adr/`。

**施主が否と言えば、ADR 0001 を `docs/design/` 側へ畳む。** 畳む場合、
`docs/coding-rules.md` と `CLAUDE.md` と PR テンプレートの参照も同時に直すこと
（`CNF-006` がリンク切れを検出するので、直し漏れは CI が落とす）。

### D-1〜D-4（`docs/design/scopegrep.md` が正本）

**D-2 が本体。** 詳細と評価軸は [`docs/todo/current.md`](../todo/current.md)。
規約から来た制約が1つある——`tree-sitter` は `build.rs` で C を実行するのが通例で、
**RS-010 がそれを禁じている**。採るなら ADR が要る。

⚠️ ただし**規約が設計を先回りして殺さないこと**。制約を明示しただけで、D-2 は決め打ちしていない。

## 5. まだ機械が見ていないもの（planned の要点）

| ID | 内容 | なぜ未実装か |
| --- | --- | --- |
| `CNF-005` | 不変条件を持つ型は自分のモジュールに単独で置く | 型情報が要る可能性。要検討 |
| `ARC-003` | 中核を `no_std` にして純粋性を構造で守る | **対象クレートがまだ無い。**切った時点で active になる |
| `QLT-008` | カバレッジ下限 | 実装が無いので測る対象が無い。**足場のテスト1本で 100% を主張しない** |
| `RS-015` | 環境・引数・標準入出力は配線点だけ | `ARC-003` と同時に active になる |
| — | `cargo-deny` | **依存が 0 なので検査対象が無い。**依存を足す ADR と同時に導入する |

🔴 **残る穴を正直に書いておく。** `#[derive(Default)]` は `CNF-001` で塞いだが、
Rust の可視性は「子モジュールが祖先の非公開項目に到達できる」ので、
**不変条件を持つ型と雑多な型を同じモジュールに同居させると、隣人がファクトリを迂回できる。**
これが `CNF-005` の対象で、現時点では**規約文書の言葉としてしか存在しない。**

## 6. このリポの性格（判断がここで変わる）

**第一目的は「Rust でツールが作れる」ことを public に示すこと**（CLAUDE.md）。
道具としての有用性は第二目的。だから:

- 本数より1本の完成度。**半端な道具が4本並ぶより、問題設定が明快な1本**
- **README が成果物の本体。**「何が問題だったか」を書く。機能一覧ではない
- **緑を保つ。**`main` が赤いリポは中身を読む前に評価が終わる
- ⚠️ **README を盛らない。** 施主は実測に基づかない主張を最も嫌う。
  書いてある失敗は実際に起きたもので、脚色しない

⚠️ **PUBLIC リポである。**`_work` 由来の実データ（案件名・顧客・金額・ハンドル）を
持ち込まない。fixture は手で書いた架空のデータにする（CLAUDE.md 地雷5）。
`scopegrep/testdata/workflow-with-comment.yml` はその方針で手書きしたもの。
