## 3. 触る前に知っておくこと

### 🔴 部分集合を広げるときの順番

**測る → 設計メモの表を先に直す → 「エラーになる」テストを「通る」テストに書き換える → 実装 → 再計測。**
v1.1 はこの順でやった（計測手順は日報第3セッション。バイナリを手元の全 `.yml` に当てて終了コード 2 を数えるだけ）。
逆にやると「読めると書いていないものを読む」状態ができ、エラーにする方針が崩れる。
**corpus に 0 件の構文は足さない。** 要るファイルが出てから測る。

### 🔴 README の例を変えるときは実行して貼る

`tests/readme.rs` が毎回照合する。手で書いた例は次の `make check` で落ちる。
`$ scopegrep` の例が 0 件になっても落ちる（空振り緑を防ぐため）。

### 🔴 規約の摩擦は解き方が分かっている

実装リナ 3 回分の解き方は日報の「規約で詰まった箇所」に列挙した。
**ゲートは 1 箇所も緩めていない。緩めたくなったら ADR（QLT-005）。**
カバレッジ下限（`Makefile` の `COVERAGE_MIN_LINES`）は上げる方向にしか動かさない。

### 🔴 依存を足すとき（ADR 0002 が前例）

既定ビルドの依存 0 を崩さない。足すなら Cargo feature で opt-in にし、core には入れない（`Matcher` trait で受ける）。
`deny.toml` の `allow` には**実際に使うライセンスだけ**書く（先回りで書くと `make deny` が落ちる）。
`make check` は両構成で回るので、feature の中だけ壊れた状態は作れない。

### `scopegrep-core` の公開 API を変えるとき

`pub use` を書けないので型はモジュール経由（`scopegrep_core::document::Document`）。
API を変えたら設計メモの「公開 API」節も同時に直す（CNF-006 はリンク切れは見るが API の食い違いは見ない）。
