## 実測でわかったこと

`nene-recall` の ADR 0010 が「Go に無い」と記録した4点を Rust で測り直した。**全部あった。**

| NENE-PIXEL の規則 | Go | Rust（実測） |

| KOT-003 公開状態は不変 | 無い | **ある**（`let` が既定で不変） |

さらに Rust には先行3事例のどれにも無いものがあった。

```
#![forbid(clippy::unwrap_used)]
#[expect(clippy::unwrap_used, reason = "テストだから")]
→ error[E0453]: expect(...) incompatible with previous forbid
```

**抑制しようとする行為そのものがコンパイルエラーになる。**
Kotlin の `@Suppress` にも Go の `//nolint` にもこれに相当するものは無い。

## 今日の判断

### 1. 抑制を二段構えにした

| 段 | 水準 | 抑制 |
| --- | --- | --- |
| 1段目 | `forbid` | **不可能**。例外を申請する窓口が存在しない |
| 2段目 | `deny` | `#[expect(lint, reason = "<規則 ID>: <理由>")]` **のみ** |

### 2. NENE-PIXEL の waiver 台帳を移植しなかった

**Rust では制度の大半をコンパイラが執行している。** forbid 層は申請窓口が無く、
deny 層の `#[expect]` は理由が必須で、不要になれば `unfulfilled_lint_expectations` が落とす。
台帳は「機械が見ていない抑制を人手で追う」ための仕組みで、**その対象がここには無い。**

⇒ 移植すると、機械が既に守っているものを人手で二重に追う形になる。却下理由は ADR に記録。

### 3. ADR の位置づけを CLAUDE.md と整理した

CLAUDE.md は「ADR 形式は取らない」と書いていたが、あれは**ツールの設計判断**についての規約。
**ゲートの判断はそれとは別の対象**で、QLT-005（ゲートを弱める変更は ADR を要する）が
定める以上、置き場が要る。⇒ 設計は `docs/design/`、ゲートは `docs/adr/`。CLAUDE.md に追記。

⚠️ **この分割は施主の未確認事項。** 異論があれば ADR 0001 を `docs/design/` 側へ畳む。

## 見つけた欠陥3件

### 1. `cognitive_complexity` が死んだ設定だった

`clippy.toml` に閾値を書いていたが、この lint は `nursery` 群にあり
`clippy::all` にも `pedantic` にも入らない。**一度も評価されていなかった。**

🔑 **設定ファイルに項目が在ることは、検査が効いていることの証明ではない。**
本物のコードだけを見ていたら永久に緑のままだった。

### 2. 検査器が自分自身を検出した

`xtask` を初めて repo に走らせたら違反7件。**全て検査器自身の検出語**だった。
ファイル単位の除外で黙らせると**そのファイルだけ他の CNF も効かなくなる**ので、
検出語を `concat!` で分割する形にした。**検査器は自分自身も検査対象である。**

### 3. 機械が判定できない条件を規約に書いていた

RS-003 を当初「**不変条件を持つ型に** `Default` を実装しない」と書いたが、
不変条件の有無は機械が判定できない。
**判定できない条件を規約に書くと、その規則は永久に planned のままになる。**
`Default` の全面禁止に変えて active にした。

## 今日の判断

1. **D-2 は手書きの行指向スキャナ（依存 0・`no_std`）。** 実測してから決めた。
   位置付きパーサ crate（`saphyr-parser` 等）は fixture を通すがコメントを捨て、依存が 7〜11 件増える。
   `tree-sitter` は C コンパイラ必須。手書きならコメント別枠表示を依存なしで後から足せる
2. **部分集合の外は黙って誤読せずエラー**（種別＋行番号）。ヒットがあってもエラーがあれば終了コード 2
3. **列は「一致の先頭」**（実装リナが仕様の矛盾を報告。規範文を採り、例の方を直した）
4. **ラベルはクォートを 1 枚外す**（値は原文のまま。ラベルは表示用の識別子なので扱いを分けた）
5. **README の例はテストが照合する。** 手で書いた例は次の `make check` で落ちる（地雷 2 を機械で塞いだ）
6. **カバレッジ下限は workspace 全体で 90**。`xtask` を除外して数字を良く見せることはしない

## 実測で分かったこと

- `saphyr-parser` / `yaml-rust2` の `Marker::col()` は doc が「1-indexed」と言いながら **0 始まり**を返す
- `tree-sitter-yaml` の木では、ステップ直前のコメントが**前のステップの子**になる
- `serde_yml` 最新版は `noyalib` へ転送するだけの shim
- `no_std` クレートで `use std::fs;` は **E0432**（式なら E0433）。証明は実出力に合わせて直した
- `cargo-llvm-cov 0.9.0` の `--fail-under-lines` は**メッセージ無しの終了コード 1**

## 実装リナが規約で詰まった箇所（全て設計側で解いた・ゲートは無変更）

`pub_use` 禁止 → 公開型は `pub mod` 経由／`module_name_repetitions` → モジュール名と型名を完全一致／
`new_without_default` × `Default` 禁止 → 引数ゼロの公開 `new` を作らない／`map_err_ignore` → `ok().ok_or_else()`／
`cargo_common_metadata` → core にも `readme`・`keywords`・`categories`／複雑度 10・60 行 → 状態を小さな型に分けた。
**予告どおり摩擦は添字と `as` の周辺で、`get()` と `try_from` で全て通った。**

# 日報 2026-09-02（第4セッション）— 毎日使える形にして、正規表現は opt-in で足した

> 担当: 設計リナ（Fable 5.1）＋ 実装リナ（Opus 5・2 回）/ 成果: PR [#4](https://github.com/hideyukiMORI/xi-tools/pull/4)（未マージ）。PR #3 は施主承認後に rebase マージ

## 施主の判断

- 「便利に使えるレベルまで対応を進めて」「`~/.cargo/bin` に入れて」
- 正規表現は「**オプションで拡張できる**」形（施主の提案）→ Cargo feature で opt-in。ADR 0002 を承認

## やったこと

| 回 | 内容 | 結果 |
| --- | --- | --- |
| 計測（設計リナ） | `node_modules` 3,206・`vendor` 3,837 の YAML。`~/docker` 全体の走査 5.6 秒・エラー 30 | 除外リストの根拠 |
| 実装 6 | `--scope`（構造で絞る）・`-i`・パス省略・除外 | テスト 239・カバレッジ 94.55%・走査 0.55 秒 |
| 実装 7 | `Matcher` trait・feature `regex`・`cargo-deny`・両構成の `make check` | テスト 258 / 270・カバレッジ 94.90%・依存は実測 3 crate（見積 5） |
| 導入 | `cargo install`（v1.1 → `--scope` 版） | `~/.cargo/bin/scopegrep` |

## 今日の判断

1. **`--scope` の `*` はセグメント 1 つ、`**` は 0 個以上。部分一致のグロブは作らない**（`*` の意味を一つに保つ）
2. **除外は固定リスト**（`.git` `node_modules` `vendor` `target` `.venv`）。`.gitignore` の解釈は依存か複雑さを要するので採らない。`dist` は施主の実フォルダ名と衝突するので入れない
3. **正規表現は core に入れない。** core は `Matcher` trait を受け取り、正規表現の実装は bin 側に feature 付きで置く。core は構成によらず `no_std`・依存 0
4. **feature 無しの binary で `-e` は終了 2**。黙って固定文字列として扱わない
5. **`cargo-deny` の許可は実際に使っているライセンスだけ**（`--deny license-not-encountered`）。opt-in の依存も `all-features = true` で検査グラフに入れる
6. **README の `-e` の例は feature 無しでは飛ばすが、飛ばした結果「検証 0 件」なら落ちる**。どの構成でも例が一度も実行されない経路を作らない

## 実測で分かったこと

- `regex` の推移的依存は `default-features = false` で **3 crate**（ADR の見積 5 は多かった。ADR に実測を追記）
- `-e` と `<needle>` の排他は機械的に判定できない（`-e x a.yml` の `a.yml` は明らかにパス）。仕様を「`-e` があれば位置引数は全部パス」に直した
- `İ` のように小文字化で長さが変わる字があるので、`-i` の列は原文で数えないとずれる（テストで固定）

## 判断

1. **依存 0 のまま**（ADR 0003）: `gh` サブプロセス・`std::thread::scope`・手書き JSON（RFC 8259・no_std）。`tokio` / `serde_json` / `ratatui` / `octocrab` は却下理由つき
2. **中核は I/O が本体でも `no_std`**: `git` / `gh` の出力を文字列で、「今日」を値で受けて表を返す。全部 fixture でテストできる
3. **`?` には必ず理由**（F-5）。行は消さない。終了コード 0/1/2
4. README の例は `text` ブロック・実行日つきで照合しない（地雷 2 の例外。`scopegrep` には逆流させない）
