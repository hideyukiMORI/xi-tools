## 次の1手: D-2 を PoC で決める

🔴 **`docs/design/scopegrep.md` が D-2 を「本体」と書いている。**
コメント内のヒットを区別できることが `grep` に対する優位の中核なので、
**ここを「動けばいい」で決めると道具の存在理由が半分消える**（CLAUDE.md 地雷1）。

### 合否を決めるファイル

[`scopegrep-core/testdata/workflow-with-comment.yml`](../../scopegrep-core/testdata/workflow-with-comment.yml)（手書きの架空データ）。

同じ `cancelled()` が3つ入っている。**候補パーサはこれを別物として区別できなければならない。**

| # | 位置 | 期待 |
| --- | --- | --- |
| 1 | コメント内の散文 | **ヒットさせない**（ここを拾うのが `awk` 版で残った偽陽性そのもの） |
| 2 | `jobs.frontend-check.steps[3].if` | 所属を返す（欠陥側） |
| 3 | `jobs.e2e.steps[2].if` | 所属を返す（正しい用法側） |

### 評価軸（規約から来る制約を含む）

| 軸 | なぜ |
| --- | --- |
| コメントと設定値を区別できるか | **これが落ちる候補は不採用**。道具の存在理由 |
| 所属パス＋行番号を持てるか | 出力の中身そのもの（D-1） |
| `build.rs` を要求するか | RS-010 が禁じている。要求するなら ADR が要る |
| 依存の数とライセンス | ARC-004。**現在の依存は 0**。増やすなら ADR |
| 中核を `no_std` に置けるか | ARC-003。置ければ時刻・環境・I/O が名前解決エラーになる |
| `HashMap` を返さないか | RS-016。出力順が実行ごとに変わると差分が取れない |

### 候補

| 候補 | 想定される強み | 想定される弱み |
| --- | --- | --- |
| **A. 手書きの行指向スキャナ** | 依存 0。`no_std` にできる。YAML のインデントは行から復元できる | YAML の全機能（アンカー・複数行スカラ・フロー記法）に弱い |
| **B. コメント保持系の YAML パーサ** | 構文木が手に入る | 依存が増える。コメントを本当に保持するか**実測が要る** |
| **C. `tree-sitter-yaml`** | コメントも位置も持てる | **`build.rs` で C を実行するのが通例**（RS-010 と衝突）。依存が重い |

⚠️ 上の「強み・弱み」は**想定であって実測ではない**。PoC で潰すこと。

### 手順

1. 各候補で「3つの `cancelled()` を区別できるか」だけを試す最小の実験を書く
   （**製品コードに入れない。**`/tmp` の使い捨てで足りる）
2. 評価軸の表を実測値で埋める
3. `docs/design/scopegrep.md` の D-2 に**決定と却下理由**を書く
4. 依存を増やす／`build.rs` を許す判断をしたなら `docs/adr/` にも1本立てる（ARC-004 / RS-010）
